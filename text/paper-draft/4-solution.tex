
\subsection{Solution Design}
    RD can be either stored on each level (PLRDF) or on the top level (TopLevel-RDF). When range deletes flush down to the disk, range deletes are merged and stored on to level 0 vector. Latter, when compaction happens, corresponding range deletes are moved and merged to the next level vector in PLRDF. While in TopLevel-RDF, range deletes are stored in the top level only, and those whose ranges intersects with the newly inserted files are removed. When either flush or compaction happens, range deletes from the topper level which are newer remove the obsolete entries from the files it compacted to on the lower level. In this way, if an entry is overlapped with a range delete tombstone in a file, it must be newer than the range delete tombstone. Sequence numbers are not required because if there are overlapping files across two levels, files on the lower level is newer and if an entry and range deletes co-exist in a file, the entry is sure to exist. \\

    \begin{itemize}
        \item \textbf{None.} Original rocksDB without RDF, it performs similar to PLRDF, while it searches for overlapping range deletes first each time before searching a specific key in a file.
        \item \textbf{PLRDF.} Range deletes are stored on each level and moved down to the next level during compaction. When a point query is blocked on a certain level, it indicates that the key doesn't exist on the levels below, requiring disk access on the current level, just the same as storing range deletes inside SST files. It performs a key search in a file first, if the key is found it return the key directly before it try to search for the overlapped key in the same file.
        \item \textbf{Split-PLRDF.} Whenever new entries arrive at a certain level, ranges that overlap with the newly inserted entries are split. This ensures that an entry existing on a certain level won't be covered by ranges in the RDF. However, this approach results in a larger memory footprint due to fragmented ranges.
        \item  \textbf{TopLevel-RDF.} RDF is limited to the top level, such that it blocks query if an entry doesn't exist in the database. It performs split function on all incoming entries, leading to larger memory footprint.
        \item \textbf{Skyline-RDF.} All the range deletes inserted are maintain in this single RDF. Keys are first found before comparing with this RDF. Because we need to deferentiate the whether a key with arbitrarity sequence number is deleted, each ranges within this RDF needs a sequence number too, so that it can tell whether a key is trully deleted. And due to the post filtering, it spent more effort than the previous RDFs, where if a range deleted was found on a certain level, originally it shall directly return but now it keeps searching for the key until a key is found or reaches the last level.
    \end{itemize}


\subsection{Solution Memory Footprint}
    Benefiting from the RD filter, there's the cost of memory footprint. In this section, we will discuss the memory footprint of each RDF. \\
    Representing range delete with a tuple or a triple, there's an start key and an end key each takes a byte. For recording the order, a sequence number of b byte is required. \\
    Furthermore, let $\alpha$ be the range split ratio in an RDF, $\beta$ be the range absorb ratio and $\gamma$ be the inserted-keys-driven split factor. All these ratio may vary with time. \\
    Suppose there are N range deletes in the RDF, then the memory footprint of each RDF is as follows: \\

    \begin{itemize}    
        \item \textbf{None.} Default RocksDB stores range deletes in each SST file where they belong to. Range Deletes are loaded when SST files are opened. The memory footprint depends on the number of opened SST files and the number of range deletes in those files. \\
        \item \textbf{PLRDF.} Memory footprint = O($N(1-\beta)2\alpha$) bytes. Tuples are enough to represent range deletes. When ranges on the same level intersect with one another, they are absorbed into one, which increases the $\beta$, range absorb ratio. However, overlapped range deletes may cumulate on different levels, which decreases $\beta$.\\
                                    It is favorable to have ranges accumulated on limited levels.
        \item \textbf{Split-PLRDF.} Memory footprint = O($N(1-\beta)(1+\gamma)2\alpha$) bytes. Similar to PLRDF, but this one suffered from inserted-keys-driven split. When a new key falls in the region of a range delete, it splitted into 2 ranges, which contributes to $\gamma$, inserted-keys-driven split factor. \\
                                    It is favorable to have less inserted keys fall into the range deletes.
        \item \textbf{TopLevel-RDF.} Memory footprint = O($N(1-\beta)(1+\gamma)2\alpha$) bytes. Like Split-PLRDF, instead ranges don't move down to the next level, so it sufferes more from the inserted-keys-driven split. \\
                                    The worst case can be a range keep split by all the inserted keys, causing an amplification of number of inserted keys.
        \item \textbf{Skyline-RDF.} Memory footprint = O($N(1+\alpha-\beta)(2\alpha-\beta)$) bytes. Triples are used to represent range deletes. When small range falls within the larger range the range split into tree segments which contributes to the $\alpha$, range split ratio; In opposite, when a larger range comes in and contain the smaller range, the ranges are absorbed into one, which contributes to the $\beta$, range absorb ratio. \\
                                    It is favorable to have larger ranges come in and absorb the old ranges.
    \end{itemize}
